# Тестирование API сервиса PetStore (Swagger/OpenAPI)

## Описание проекта
Данный проект демонстрирует практический опыт тестирования REST API с использованием инструмента **Postman**. В качестве объекта тестирования был выбран публичный сервис **PetStore (`https://petstore.swagger.io/`)**, документация к которому предоставлена в формате Swagger/OpenAPI.

## Цель проекта
*   Отработка навыков тестирования REST API, включая тестирование всех HTTP-методов (GET, POST, PUT, DELETE).
*   Создание структурированной коллекции запросов в Postman.
*   Использование переменных для упрощения работы и поддержки.
*   Настройка авторизации для доступа к защищенным эндпоинтам.
*   Анализ статус-кодов, форматов тел запросов и ответов.
*   Демонстрация понимания важности API-тестирования для раннего обнаружения дефектов.

## Используемые инструменты и технологии
*   **API:** REST, Swagger/OpenAPI (`https://petstore.swagger.io/`)
*   **Инструмент тестирования:** Postman
*   **Форматы данных:** JSON, XML
*   **HTTP:** Методы (GET, POST, PUT, DELETE), статус-коды (2xx, 4xx, 5xx)
*   **Авторизация:** API Key (`client_id` = "тест")

## Ключевые задачи и решения

### 1. Создание коллекции в Postman
*   Разработана **коллекция запросов**, охватывающая все основные ресурсы сервиса PetStore (Pet, Store, User).
*   Каждый ресурс протестирован с использованием соответствующих HTTP-методов:
    *   `GET` (получение списка, получение по ID)
    *   `POST` (создание нового ресурса)
    *   `PUT` (обновление существующего ресурса)
    *   `DELETE` (удаление ресурса)

### 2. Использование переменных
*   Настроены **Environment Variables** в Postman для:
    *   **Base URL:** `https://petstore.swagger.io/v2/` (чтобы избежать повторного ввода URL в каждом запросе).
    *   **Client ID:** `test` (для авторизации).
*   Переменные используются во всех запросах, что обеспечивает гибкость и легкую поддержку коллекции.

### 3. Настройка авторизации
*   Для доступа к эндпоинтам, требующим авторизации (например, для просмотра и редактирования домашних питомцев), настроен механизм авторизации **API Key**.
*   Введено значение `test` в поле `client_id` согласно требованиям задания.

### 4. Тестирование запросов и анализ ответов
*   **Статус-коды:** Особое внимание уделено проверке корректных статус-кодов ответов (например, 200 OK, 201 Created, 400 Bad Request, 404 Not Found).
*   **Тело запроса (Request Body):**
    *   Тестирование корректности **JSON-формата** для POST и PUT запросов.
    *   Проверено наличие и корректность **обязательных атрибутов** (например, `id`, `name`, `status` для Pet).
*   **Тело ответа (Response Body):** Анализ полученных данных в формате JSON/XML на соответствие ожидаемому.
*   **Валидация:** Тестирование поведения API при отправке некорректных данных (например, невалидные ID, пропущенные обязательные поля).

### 5. Практическая значимость API-тестирования
*   Продемонстрировано, как API-тестирование позволяет находить критические баги на интеграционном уровне, еще до начала тестирования GUI.
*   Подчеркнута важность использования Swagger/OpenAPI документации как основного источника информации для тестировщика.
